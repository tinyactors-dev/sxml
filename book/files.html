The sxml Book

Files and the Outside World

A query or a stylesheet often needs more than its input: another document, a text file, a module, a schema. This chapter explains how sxml finds them, and how it keeps a query from reading or writing what it shouldn't. The examples are in docs/book/examples/spec, with the Vane draft and its references.

Resolvers

The sxml library itself never opens a file or a network connection. Whenever it needs a resource, such as the document for fn:doc, the text for fn:unparsed-text, a module for import module or a schema for import schema, it asks a resource resolver that the program using it provides. The resolver gets the kind of resource and its absolute URI, and answers with the bytes, or with nothing.

That one rule makes sxml safe to embed. A web server that renders users' drafts can give them a resolver that knows the draft and the bibliography and nothing else. A browser page can answer from memory. A test can answer from a table. Embedding sxml in C shows how to write one in C, and sxml in JavaScript in JavaScript.

Files and the sxml command

The sxml command's resolver reads local files, and only those. URIs are resolved against the static base URI, which for an expression on the command line is the working directory:

$ sxml xpath 'doc("vane-00.xml")/rfc/@docName/string()'
"draft-example-vane-protocol-00"
$ sxml xpath 'unparsed-text-lines("publish.sh")[1]'
"#!/bin/sh"

The same holds for sxml xquery, whether the query is in a file or not. In a stylesheet, relative URIs are resolved against the stylesheet's own location, as XSLT expects. A resource that isn't there is an error, with the code the specification gives, and a URI that is not a local file is never fetched, not even the RFC Editor's bibliography:

$ sxml xpath 'doc("vane-02.xml")'
expression:1:1: err:FODC0002: The file cannot be read (vane-02.xml)
$ sxml xpath 'doc("https://www.rfc-editor.org/refs/bibxml/reference.RFC.2119.xml")'
expression:1:1: err:FODC0002: Only local files are available (https://www.rfc-editor.org/refs/bibxml/reference.RFC.2119.xml)

doc-available and unparsed-text-available ask first:

$ sxml xpath 'doc-available("vane-02.xml"), unparsed-text-available("publish.sh")'
false()
true()

External entities and DTDs

An XML document can pull in other files itself, through its DTD. For years, xml2rfc authors wrote their references that way: the RFC Editor publishes a file for each RFC (its bibxml), and a draft declares an external entity for each one it cites. bibxml/ holds the four the Vane draft needs:

bibxml/reference.RFC.2119.xml:

<?xml version="1.0" encoding="UTF-8"?>
<reference anchor="RFC2119" target="https://www.rfc-editor.org/info/rfc2119">
  <front>
    <title>Key words for use in RFCs to Indicate Requirement Levels</title>
    <author fullname="S. Bradner" initials="S." surname="Bradner"/>
    <date year="1997" month="March"/>
  </front>
  <seriesInfo name="BCP" value="14"/>
  <seriesInfo name="RFC" value="2119"/>
</reference>

vane-entities.xml, a short version of the draft, refers to them, and its internal DTD subset declares a default for an attribute:

<?xml version="1.0" encoding="UTF-8"?>
<!-- The references of the Vane draft, as xml2rfc authors used to write
     them: each reference is an external entity, a file of the RFC
     Editor's bibliography (bibxml), and the DTD gives every reference a
     default for the attribute quoteTitle. -->
<!DOCTYPE rfc [
  <!ENTITY RFC2119 SYSTEM "bibxml/reference.RFC.2119.xml">
  <!ENTITY RFC5234 SYSTEM "bibxml/reference.RFC.5234.xml">
  <!ENTITY RFC6238 SYSTEM "bibxml/reference.RFC.6238.xml">
  <!ENTITY RFC8174 SYSTEM "bibxml/reference.RFC.8174.xml">
  <!ATTLIST reference quoteTitle (true | false) "true">
]>
<rfc version="3" docName="draft-example-vane-protocol-01">
  <front>
    <title>The Vane Protocol for Feature Flag Rollouts</title>
  </front>
  <middle>
    <section anchor="terminology">
      <name>Terminology</name>
      <t>The key words are to be interpreted as described in BCP 14
      <xref target="RFC2119"/> <xref target="RFC8174"/>.</t>
    </section>
  </middle>
  <back>
    <references anchor="normative">
      <name>Normative References</name>
      &RFC2119;
      &RFC5234;
      &RFC8174;
    </references>
    <references anchor="informative">
      <name>Informative References</name>
      &RFC6238;
    </references>
  </back>
</rfc>

Reading those files when a document asks for them is a classic security hole, so sxml doesn't, unless you say so. sxml check skips external entities without --external-entities, and fn:doc refuses a document that needs them unless the call trusts it:

$ sxml check vane-entities.xml
$ sxml check --external-entities vane-entities.xml
$ sxml xpath 'doc("vane-entities.xml")//reference/@anchor'
expression:1:1: err:FODC0016: The document refers to an external DTD or entity, and the call does not trust external resources (F&O 4.0, fn:doc, fn:parse-xml: trust-external)
$ sxml xpath 'doc("vane-entities.xml", { "trust-external": true() })//reference ! `{@anchor} {@quoteTitle}: {front/title}`'
"RFC2119 true: Key words for use in RFCs to Indicate Requirement Levels"
"RFC5234 true: Augmented BNF for Syntax Specifications: ABNF"
"RFC8174 true: Ambiguity of Uppercase vs Lowercase in RFC 2119 Key Words"
"RFC6238 true: TOTP: Time-Based One-Time Password Algorithm"

The trusted parse read the four entities, each a file below bibxml/, and the DTD added the default attribute quoteTitle="true" to every reference, though no file writes it. Entities that expand to too much text are stopped by a limit, so a small document can't expand into gigabytes. Today's xml2rfc reads references with xi:include instead of entities; the risk and the rule are the same.

Writing files

The sxml command writes a file only when an option names it:

OptionWhat it writes
--output=FILEthe result of xpath, xquery, transform or serialize
--result-directory=DIRthe result documents of transform, below DIR
--allow-putthe documents that fn:put stores in xquery
--allow-file-accessanything the EXPath File functions write

Files are written only when the command succeeds, each in one step, so a failed run never leaves half a file behind. A file that exists is replaced only with --force. Project: Publishing the Specification relies on both rules.

EXPath File

The EXPath File functions read and write files and directories directly, with the prefix file. Because they can touch any file the user can, they exist only with --allow-file-access:

$ sxml xpath 'file:exists("bibxml")'
expression:1:1: err:XPST0017: no function with this name and arity is known
$ sxml xpath --allow-file-access 'sort(file:list("bibxml")) ! doc("bibxml/" || .)/reference ! `{@anchor}: {front/date/@year}`'
"RFC2119: 1997"
"RFC5234: 2008"
"RFC6238: 2011"
"RFC8174: 2017"
$ sxml xpath --allow-file-access 'file:create-dir("notes"), file:write-text-lines("notes/references.txt", sort(file:list("bibxml"))), file:read-text-lines("notes/references.txt")'
"reference.RFC.2119.xml"
"reference.RFC.5234.xml"
"reference.RFC.6238.xml"
"reference.RFC.8174.xml"
$ cat notes/references.txt
reference.RFC.2119.xml
reference.RFC.5234.xml
reference.RFC.6238.xml
reference.RFC.8174.xml

file:list gives the names in a directory, in no particular order, so the query sorts them. Without the option, the functions don't exist at all, as if sxml had never heard of them.

EXPath Binary

The EXPath Binary functions, with the prefix bin, work on binary data: bytes, numbers in binary encodings, and text in any encoding. They don't touch files, so they are always there. unparsed-binary reads a resource as bytes, through the same resolver as everything else:

$ sxml xpath 'unparsed-binary("vane.xml") => bin:part(0, 5) => bin:to-octets()'
60
63
120
109
108
$ sxml xpath 'unparsed-binary("vane.xml") => bin:part(0, 5) => bin:decode-string()'
"<?xml"
$ sxml xpath 'bin:hex("EFBBBF") => bin:to-octets()'
239
187
191
$ sxml xpath 'bin:decode-string(bin:from-octets((86, 97, 110, 101)))'
"Vane"

The bytes EF BB BF are the UTF-8 byte order mark. Some editors write it at the start of a file, and some tools that process drafts don't expect it. A file that starts with one, and a check that finds it, with a hex dump of the first three bytes of each file:

$ printf '\357\273\277<rfc/>\n' > bom.xml
$ sxml xpath '("vane.xml", "bom.xml") ! `{.}: {xs:hexBinary(bin:part(unparsed-binary(.), 0, 3))}`'
"vane.xml: 3C3F78"
"bom.xml: EFBBBF"
$ sxml xpath '("vane.xml", "bom.xml")[bin:part(unparsed-binary(.), 0, 3) = bin:hex("EFBBBF")]'
"bom.xml"

unparsed-binary gives an xs:base64Binary; cast to xs:hexBinary, the same bytes are written in hexadecimal. An XML parser skips the mark, so sxml check bom.xml finds nothing wrong: only the bytes tell.
