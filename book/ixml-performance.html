The sxml Book

Invisible XML Performance

An iXML grammar can describe any context-free language, and a parser for all of them must be able to keep many readings of the input open at once. That is more work than a parser made for one fixed language, such as sxml's XML parser, does. This chapter says how much work, which grammars sxml parses in time proportional to the input, and how to write grammars that stay fast on inputs of many megabytes.

Memory is the most memory the process held, about 10 MB of it the program itself; per MB is how much more each further megabyte of input takes, the memory the parse and its XML really cost. The XML tree of the log, an element and three attributes for each line and the messages as text, takes about 9 bytes for each character of the log; the parse adds about one more, and lets go of all of it before the query goes on.

A 1 MB log, made by a query:

make-log.xq:

(: Writes a log of $lines lines in the format of log.ixml. :)
declare variable $lines external;
string-join(
  for $number in 1 to xs:integer($lines)
  let $time := xs:time("00:00:00") + xs:dayTimeDuration("PT1S") * ($number mod 86400)
  let $level := ("INFO", "WARN", "ERROR")[$number mod 3 + 1]
  return `2026-10-20 {$time} {$level} message {$number}`,
  "&#10;"
)

$ sxml xquery --method=text --param=lines=25000 --output=big.log make-log.xq
$ sxml xpath 'string-length(unparsed-text("big.log"))'
972227
$ sxml xquery --method=text --param=file=big.log count-levels.xq
ERROR 8333
INFO 8333
WARN 8334

count-levels.xq is the grouping query of the log task, reading the file that $file names.

Which grammars are linear

sxml parses with Earley's algorithm, which reads the input once, from left to right, and keeps a set of items for each position: the rules that a reading could be in the middle of there. The work is the number of items, and five refinements keep it in proportion to the input and small:

  • One character of lookahead. An item is kept only when the next character can continue it, so the parser does not follow readings that the next character already rules out. A rule that could end anywhere, such as ~[#a]*, ends only where the next character can follow it.
  • Leo's items for right recursion. A rule that ends with itself, such as rest: ",", number, rest?, would otherwise complete once for every level of the recursion at every place the list could end; sxml completes the whole chain at once.
  • Compiled character classes. Each character of the input is looked up once in a table that says which of the grammar's character sets it belongs to.
  • Groups written out. A group or an option, such as (char; em) or inline?, and a hidden rule of one character set, such as -digit, is replaced where it is used, so the parser does not complete a rule of its own for every character. The XML is the same.
  • Regular rules read at once. A rule such as @date: digit, digit, ... or message: ~[#a]* needs no nesting: it is made of characters, character sets, repetitions and other such rules, without recursion, so its language is regular. When its XML is nothing but its text, as for a hidden rule, an attribute, or an element with only text inside, sxml compiles it once, with the grammar, into an automaton. The parser runs the automaton over the input in one step instead of making items for every character, and completes the rule at each place it can end where the next character can follow it. The XML is the same, and so is an ambiguity inside such a rule: the automaton counts the ways it reaches each end.

With these, the parser is linear on every grammar that has one reading for each input and can tell, at each place, how to go on with a bounded look ahead: the LR-regular grammars of parsing theory (Joop Leo, 1991). They include left recursion, right recursion, nesting, repetition and every grammar of Real Tasks. A right-recursive list of 200,000 numbers:

numbers.ixml:

numbers: number, rest?, -#a?.
-rest: -",", number, rest?.
number: ["0"-"9"]+.

$ sxml xpath --method=text --output=numbers.txt 'string-join(1 to 200000, ",")'
$ sxml xpath 'count(invisible-xml(unparsed-text("numbers.ixml"))(unparsed-text("numbers.txt"))//number)'
200000

Brackets nested 100,000 deep:

$ sxml xpath 'count(invisible-xml("nest: -""("", nest?, -"")"".")(string-join(((1 to 100000) ! "(", (1 to 100000) ! ")")))//nest)'
100000

Large inputs

The parser needs memory for its items and for the parse tree it reads out of them. A rule read at once makes no items inside it and one node for all its text; characters and hidden rules that the XML leaves out make no nodes, and neighbouring characters share one. So the memory follows the rules the parser cannot read at once, and is small when a grammar's text is in rules that it can: the log needs some 15 items and 9 nodes for each line of about 60 characters. All of it is released when the XML is built.

A log of 10 MB:

$ sxml xquery --method=text --param=lines=250000 --output=bigger.log make-log.xq
$ sxml xpath 'string-length(unparsed-text("bigger.log"))'
9972228
$ sxml xquery --method=text --param=file=bigger.log count-levels.xq
ERROR 83333
INFO 83333
WARN 83334

Ambiguous grammars

A grammar with many readings costs more. This one says nothing about how a sum groups, so a sum of n numbers has as many readings as there are ways to put in brackets, which grows faster than any power of n:

sum.ixml:

sum: sum, -"+", sum; number.
number: ["0"-"9"]+.

$ sxml xpath 'let $sum := invisible-xml(unparsed-text("sum.ixml"))(string-join(1 to 300, "+")) return (count($sum//number), string($sum/sum/@*:state))'
300
"ambiguous"

sxml never lists the readings. It keeps one for each item, so the items grow with the square of the input and the time with its cube: 2,000 characters take one to two seconds, eight times as long as 1,000. The cure is the cure of Writing Grammars: say how the parts group, here sum: sum, -"+", number; number., and the grammar is linear again.

Steps and limits

Every item the parser makes, every node of the parse tree, and every run of an automaton, with one more for every 16 characters it reads, counts as one step of the evaluation, so the step limit that stops a runaway query in a program stops a runaway parse too (The step limit). A linear grammar makes a few items for each character that no automaton reads, so the library's default limit of 108 steps allows inputs of many megabytes: the log of 100 MB parses within it. A host that embeds sxml can set a higher limit (Chapter "Embedding sxml in C"). The sxml command sets none: a parse there runs to its end, however long the input.

Compared with tree-sitter

Source Code as XML parses code with tree-sitter, the parser generator behind the syntax highlighting of many editors. The two take different routes to a parse. A tree-sitter grammar is a JavaScript program that a generator turns, ahead of time, into a table of an LR parser in C, compiled into the program that uses it; sxml comes with a few. An iXML grammar is text that sxml compiles while the query runs, and the parser follows every reading the grammar allows. So tree-sitter takes only the grammars its generator accepts, and needs a build step for a new one; iXML takes any context-free grammar, at run time, ambiguous ones too. Faced with a mistake in the input, tree-sitter recovers, marks the place with an ERROR node and goes on, as an editor needs; an iXML parse fails, with the place where it failed (When a Parse Fails).

The trees differ as well. The same JSON both ways:

json.ixml:

json: -s, value, -s.
-value: object; array; string; number; true; false; null.
object: -"{", -s, (member, (-s, -",", -s, member)*)?, -s, -"}".
member: @name, -s, -":", -s, value.
array: -"[", -s, (value, (-s, -",", -s, value)*)?, -s, -"]".
@name: -'"', ~['"\']*, -'"'.
string: -'"', ~['"\']*, -'"'.
number: "-"?, ["0"-"9"]+, (".", ["0"-"9"]+)?, (["eE"], ["+-"]?, ["0"-"9"]+)?.
true: -"true".
false: -"false".
null: -"null".
-s: -[" "; #9; #a; #d]*.

$ sxml xpath --method=xml 'invisible-xml(unparsed-text("json.ixml"))(unparsed-text("flag.json"))'
<json><object><member name="flag"><string>dark-mode</string></member><member name="rollout"><number>25</number></member><member name="owners"><array><string>web</string></array></member></object></json>
$ sxml xpath --method=xml 'tree-sitter:parse(unparsed-text("flag.json"), "json", { "highlights": false() })'
<document xmlns:sxml="urn:sxml"><object>{<pair><string field="key">"<string_content>flag</string_content>"</string>: <string field="value">"<string_content>dark-mode</string_content>"</string></pair>, <pair><string field="key">"<string_content>rollout</string_content>"</string>: <number field="value">25</number></pair>, <pair><string field="key">"<string_content>owners</string_content>"</string>: <array field="value">[<string>"<string_content>web</string_content>"</string>]</array></pair>}</object>
</document>

The grammar says what the XML is: hidden rules and strings leave the punctuation out, and the names become attributes. Tree-sitter's tree keeps every character of the text, the punctuation as text between the elements, and names its elements after the grammar's rules.

In time the two are close. The same benchmark suite parses 1 MB of JSON and the Markdown input of the table above both ways, and JSON with fn:json-to-xml too, sxml's hand-written JSON parser. The numbers are for the whole command, as above:

The rest is the XML tree, which has twice as many elements as the iXML grammar makes. A parser made for one language in advance, fn:json-to-xml, is faster than both, but not by much.

Markdown is two grammars in tree-sitter, one for the blocks and one for the text inside them, and its grammar for the blocks keeps several readings open where Markdown is unclear; it parses all of CommonMark, where markdown.ixml knows the few constructs of Real Tasks. The inline grammar is parsed anew for every paragraph, as a layer of its own (Code inside code). Both grow linearly with the input.

Writing fast grammars

  1. Avoid ambiguity. It is the one thing that makes a parse more than linear, and it is a mistake in the grammar anyway.
  2. Hide what you do not need. Hidden rules and strings make no elements, so the tree is smaller and the query after the parse is faster.
  3. Use character sets for runs of characters. [L]+ is one set read many times; letter+ with letter: "a"; "b"; ... is one rule with many alternatives at every character.
  4. Keep text in rules of its own. A rule whose XML is just its text is read at once when it is regular (see above). A mark or an insertion inside it, or a hidden character among visible ones, such as the -'"' of a quoted field, makes it an ordinary rule again: leave such parts to the rule around it, as -quoted: -'"', text, -'"' with -text: ~['"']* does.
  5. Compile once. Keep the parser in a variable and call it for every input (Compile once).
