The sxml Book

Checking the State Machine

Checking What the Schema Cannot checked the flag's state machine with a query: every state can be reached, every event the machine handles is declared and every declared event is used, payloads and types name something in vane-data.xsd, data values fit their types, and the requirements the machine names exist in the draft. This chapter writes the same checks as a Schematron schema, in the scxml directory, and compares the two.

The schema

flag.sch:

<?xml version="1.0" encoding="UTF-8"?>
<!-- Rules of a Vane machine that its schemas cannot say. The context of
     every rule is a node of the machine; vane.xml is the draft it
     implements, vane-data.xsd the schema of its data. -->
<schema xmlns="http://purl.oclc.org/dsdl/schematron"
        xmlns:xsl="http://www.w3.org/1999/XSL/Transform"
        queryBinding="xslt3" schematronEdition="2025">
  <title>Rules of a Vane machine</title>
  <ns prefix="sc" uri="http://www.w3.org/2005/07/scxml"/>
  <ns prefix="vane" uri="urn:example:vane"/>
  <ns prefix="xs" uri="http://www.w3.org/2001/XMLSchema"/>
  <ns prefix="check" uri="urn:example:check"/>

  <let name="declared" value="//vane:event/@name ! string()"/>
  <let name="implemented" value="//@vane:implements ! tokenize(.)"/>

  <!-- The machine alone, for a sketch that names no requirement yet. -->
  <phase id="machine" when="empty(//@vane:implements)">
    <active pattern="states"/>
    <active pattern="events"/>
    <active pattern="data"/>
  </phase>

  <pattern id="states">
    <!-- Every state a path of transitions leads to from the initial one. -->
    <let name="reachable" value="
      let $states := //(sc:state | sc:final)
      return fold-left(1 to count($states), string(/sc:scxml/@initial),
        fn($reached, $pass) {
          distinct-values(($reached,
            $states[@id = $reached]//sc:transition/@target ! tokenize(.)))
        })"/>
    <rule context="sc:state">
      <assert id="reachable" test="@id = $reachable">No transition leads
        to the state <value-of select="@id"/>.</assert>
    </rule>
  </pattern>

  <pattern id="events">
    <rule context="sc:transition[@event]" visit-each="tokenize(@event)">
      <assert id="declared" test=". = $declared">The event
        <value-of select="."/> is not declared in vane:events.</assert>
    </rule>
    <rule context="vane:event">
      <assert id="used" severity="warning"
              test="@name = (//sc:transition/@event ! tokenize(.),
                             //(sc:send | sc:raise)/@event)">Nothing
        handles, sends or raises the event <value-of select="@name"/>.</assert>
    </rule>
  </pattern>

  <!-- The simple types of vane-data.xsd: each has a constructor function. -->
  <xsl:import-schema namespace="urn:example:vane" schema-location="vane-data.xsd"/>

  <!-- Whether a value is one of a type: a cast that fails is false. -->
  <xsl:function name="check:fits" as="xs:boolean">
    <xsl:param name="value" as="xs:string"/>
    <xsl:param name="type" as="xs:QName"/>
    <xsl:try select="exists(function-lookup($type, 1)($value))">
      <xsl:catch select="false()"/>
    </xsl:try>
  </xsl:function>

  <pattern id="data">
    <let name="schema" value="doc('vane-data.xsd')/xs:schema"/>
    <rule context="vane:event[@vane:payload]">
      <assert id="payload"
              test="resolve-QName(@vane:payload, .)
                    = $schema/xs:element/@name ! QName($schema/@targetNamespace, .)">The
        payload <value-of select="@vane:payload"/> of <value-of select="@name"/>
        is no element of vane-data.xsd.</assert>
    </rule>
    <rule context="sc:data[@vane:type]">
      <let name="type" value="resolve-QName(@vane:type, .)"/>
      <assert id="type" test="exists(function-lookup($type, 1))">The
        type <value-of select="@vane:type"/> of <value-of select="@id"/>
        is no simple type of vane-data.xsd.</assert>
      <assert id="value" test="empty(function-lookup($type, 1))
                               or check:fits(@expr, $type)">The value
        <value-of select="@expr"/> of <value-of select="@id"/> is not a
        <value-of select="@vane:type"/>.</assert>
    </rule>
  </pattern>

  <pattern id="requirements">
    <let name="anchors" value="doc('vane.xml')//t/@anchor ! string()"/>
    <rule context="*[@vane:implements]" visit-each="tokenize(@vane:implements)">
      <assert id="known-requirement" test=". = $anchors">The draft has
        no requirement <value-of select="."/>.</assert>
    </rule>
  </pattern>

  <pattern id="draft">
    <rule context="/sc:scxml"
          visit-each="doc('vane.xml')//t[bcp14 = ('MUST', 'MUST NOT')]/@anchor ! string()">
      <assert id="implemented" severity="warning" test=". = $implemented">Nothing
        in the machine implements the draft's <value-of select="."/>.</assert>
    </rule>
  </pattern>
</schema>

Reading the schema

Two prefixes, sc for SCXML and vane for Vane's own attributes and elements, are declared with ns, as the machine declares them with xmlns; the names in the rules use them.

States. The pattern's variable $reachable is the computation of local:reachable in check.xq, written as one XPath expression: a let, then fold-left over as many passes as there are states, each adding the targets of the states reached so far. tokenize splits each target, which SCXML allows to be a list of states (see XSD 1.1 Features). A pattern's variable is evaluated once, for the whole machine, and then each state is only compared with it.

Events. A transition's event attribute holds a list of event names, so the rule visits each name (visit-each, from Patterns, Rules and Assertions) and asserts that it is declared. The finding points at the transition that waits for the undeclared event, where the query could only name the event. An unused event is a warning: it is harmless, and an owner may be about to use it.

Data. $schema reads vane-data.xsd as a document, as the query did, and the payload rule compares QNames. resolve-QName turns the attribute's text, vane:rollout, into a QName with the namespace the prefix vane has in the machine, so the machine could use another prefix and still pass. For types, the schema needs XSLT itself, which the next section explains.

Requirements. doc('vane.xml') reads the draft. A relative URI in a rule resolves against the schema's own location, so the draft is found next to flag.sch, wherever the machine is. The first rule checks the anchors the machine names; the last one goes the other way. Its context is the machine's root, and it visits each anchor of a MUST or MUST NOT requirement of the draft: the items are strings from another document, and each finding is reported at the machine's root element, line 2, which is what it is about.

XSLT inside a schema

queryBinding="xslt3" says more than which language the tests are in: under an XSLT binding, a schema can hold XSLT declarations, and sxml compiles them into the stylesheet it makes of the schema. flag.sch uses two:

  • xsl:import-schema imports vane-data.xsd, so its simple types are known, and each has a constructor function. function-lookup($type, 1) finds the constructor of a type by its name, as check.xq did; it is empty when the type does not exist, which is the type check.
  • xsl:function declares check:fits, which calls the constructor with a value and says whether that works. A constructor raises an error for a value that is not one of its type, and an XPath expression cannot catch errors; xsl:try can, so the function returns false() instead. The query did the same with XQuery's validate and try.

A test that raised the error itself would stop the validation, so the assertion value calls the function only for types that exist.

What Schematron does better

The checks are the same, and so are their answers. What changed is everything around them:

  • Places. Each finding has its line and column in the machine, and the place of the rule in the schema. check.xq printed names and left the reader to search for them.
  • Messages. Each assertion has its own message, written as a sentence, next to its test. The query built its lines in the expressions that computed them.
  • Levels. An unused event and a requirement nothing implements yet are warnings; the rest are errors. The query had one level: every line was a problem.
  • Exit status. sxml validate exits with 1 when there is an error, and 0 when there are only warnings, so a build runs it as it is. The query needed a shell test around its output.
  • Reports for programs. The same findings are available as JSON and as SVRL, the report format of the standard (Reports, Errors and Exit Statuses).

Phases

Not every check fits every moment. While an owner sketches a new machine, it names no requirements yet, and comparing it with the draft gives nothing but warnings. A phase names a set of patterns to run: machine runs states, events and data, and leaves the draft alone. --phase chooses it:

$ sxml validate --schematron=flag.sch --phase=machine flag.scxml
flag.scxml:92:3: reachable: No transition leads to the state archived. (flag.sch:34:7)
flag.scxml:31:5: used warning: Nothing handles, sends or raises the event flag.archived. (flag.sch:45:7)
flag.scxml:75:5: declared: The event flag.evaluated is not declared in vane:events. (flag.sch:41:7)

Without --phase, the schema's defaultPhase attribute chooses, and without that, every pattern runs (#ALL). The 2025 edition adds a third way: with --phase='#ANY', each document chooses for itself. The first phase, in the order of the schema, whose when expression is true for the document is used; if none is, every pattern runs. machine's when is true for a machine that names no requirement. Remove the vane:implements attributes, and the sketch gets the machine's checks, while the full machine gets all of them:

$ sed 's/ vane:implements="[^"]*"//' flag.scxml > sketch.scxml
$ sxml validate --schematron=flag.sch --phase='#ANY' sketch.scxml flag.scxml
sketch.scxml:92:3: reachable: No transition leads to the state archived. (flag.sch:34:7)
sketch.scxml:31:5: used warning: Nothing handles, sends or raises the event flag.archived. (flag.sch:45:7)
sketch.scxml:75:5: declared: The event flag.evaluated is not declared in vane:events. (flag.sch:41:7)
flag.scxml:92:3: reachable: No transition leads to the state archived. (flag.sch:34:7)
flag.scxml:31:5: used warning: Nothing handles, sends or raises the event flag.archived. (flag.sch:45:7)
flag.scxml:75:5: declared: The event flag.evaluated is not declared in vane:events. (flag.sch:41:7)
flag.scxml:2:1: implemented warning: Nothing in the machine implements the draft's req-1. (flag.sch:96:7)

A phase can also have variables of its own, and a from expression that selects the nodes its patterns start from instead of the whole document. A phase that the schema does not have is an error:

$ sxml validate --schematron=flag.sch --phase=quick flag.scxml
flag.sch:5:1: schematron:phase: the schema has no phase of this id (5.4.13): quick

What still needs XQuery

Schematron reports; it never changes a document or makes a new one. Two parts of the state-machine project stay queries and stylesheets:

  • Fixing. fix.xq makes the fixed machine with an update, and Schematron's findings say where to look but not what to write. Running flag.sch after the fix, as above, is how a build knows the fix worked.
  • Making things from the machine. The documentation of Documenting the Machine in XHTML and the drawing of Drawing the Machine are outputs, not findings.

A check whose answer is a list of problems belongs in Schematron. A check that is part of a larger computation, such as the generator's own check of the types in The rule the schema couldn't check, may stay in the program that needs it; Rules Across Documents writes that one as a rule too.
