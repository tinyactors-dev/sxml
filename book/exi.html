The sxml Book

Compact XML with EXI

XML text is easy to read and expensive to move. A feed of forty orders, orders.xml in docs/book/examples/exi, is 13,732 bytes, and most of them are the same names written again and again: <order, </line>, quantity=. EXI, the Efficient XML Interchange format of the W3C, writes the same document as a stream of events in which a name is written once and referred to by a small number after that, and in which each event takes only the bits that tell it apart from the events that could have come instead. sxml reads and writes EXI 1.0 in all its forms, and Canonical EXI, which gives one stream for one document.

Encoding and decoding

sxml encode writes the EXI stream of an XML document, and sxml decode writes the XML text of an EXI stream:

$ sxml encode --output=orders.exi orders.xml
$ sxml xpath '("orders.xml", "orders.exi") ! `{.}: {bin:length(unparsed-binary(.))} bytes`'
"orders.xml: 13732 bytes"
"orders.exi: 2390 bytes"
$ sxml decode orders.exi | head -4
<orders date="2026-11-27">
  <order id="A-1001" status="shipped">
    <customer><name>Frances Allen</name><city>Lyon</city><country>FR</country></customer>
    <line sku="KB-104" quantity="3" price="89.00">Mechanical keyboard</line>

The stream is a sixth of the text, and nothing was compressed yet: the saving is all in how the events are written. Without --output, both commands write to standard output, so they fit in a pipe.

The comment at the top of orders.xml is gone. EXI keeps what most applications read, the elements, attributes and text, and leaves out comments, processing instructions, the document type declaration and namespace prefixes unless asked to keep them. That choice is one of the stream's options.

Options

Two programs exchanging EXI agree on its options: what the stream keeps, how its bits are laid out, and whether it is compressed. The decoder needs the options the encoder used; a stream can carry them in its header (--include-options), or the two sides agree on them beforehand, as these examples do by giving both commands the same flags.

What a stream keeps is set with --preserve, a list of comments, pis, dtd, prefixes and lexical-values. invoice.xml has a comment and a namespace prefix:

$ sxml encode --output=invoice.exi invoice.xml
$ sxml decode invoice.exi
<ns0:invoice xmlns:ns0="urn:example:invoice" number="2026-0412">
  
  <ns0:order ref="A-1007"/>
  <ns0:amount currency="EUR">113.40</ns0:amount>
</ns0:invoice>
$ sxml encode --preserve=comments,prefixes --output=invoice-full.exi invoice.xml
$ sxml decode --preserve=comments,prefixes invoice-full.exi
<inv:invoice xmlns:inv="urn:example:invoice" number="2026-0412">
  <!-- Net 30 days. -->
  <inv:order ref="A-1007"/>
  <inv:amount currency="EUR">113.40</inv:amount>
</inv:invoice>

Without prefixes, the names keep their namespace and lose their prefix, so the decoder makes one up (ns0). The document means the same to any namespace-aware reader, and the comment's line is still there, since the white space around it is text.

How the bits are laid out is the alignment. The default, bit-packed, writes each event in as few bits as it needs. byte-alignment starts every value on a byte, which is larger but easier to look at in a hex dump. pre-compression and compression regroup the stream: the structure first, then the values of each attribute and element together, because values of one name are alike, and compression runs each group through DEFLATE, the algorithm of gzip:

$ sxml encode --alignment=byte-alignment --output=orders.byte.exi orders.xml
$ sxml encode --alignment=compression --output=orders.deflate.exi orders.xml
$ gzip -9 -c orders.xml > orders.xml.gz
$ sxml xpath '("orders.byte.exi", "orders.deflate.exi", "orders.xml.gz") ! `{.}: {bin:length(unparsed-binary(.))} bytes`'
"orders.byte.exi: 3862 bytes"
"orders.deflate.exi: 1011 bytes"
"orders.xml.gz: 1285 bytes"

The compressed stream is smaller than the gzip of the text, and it is still EXI: a decoder reads its events one after another, without writing the text first. For a stream that has to be small, use compression; for one that has to be fast to write and read, the default.

The other options are --fragment, for a stream of several elements with no document around them, --block-size, the number of values a compressed stream groups at a time, and --value-max-length and --value-partition-capacity, which bound the table of values the encoder remembers. Each one changes the stream, so the decoder needs the same.

With a schema

The streams so far are schema-less: the decoder knows nothing of the document before it starts, so every name is written in full the first time it appears, and every value as text. When both sides have the document's schema, the encoder writes the document against the grammar the schema gives: the names it declares are known from the start, an element the content model expects next takes no bits at all to name, and a value of a simple type is written as that type, a decimal as its digits and an enumeration as its index. orders.xsd is a schema of the order feed:

$ sxml encode --schema=orders.xsd --output=orders.schema.exi orders.xml
$ sxml encode --schema=orders.xsd --alignment=compression --output=orders.schema.deflate.exi orders.xml
$ sxml xpath '("orders.schema.exi", "orders.schema.deflate.exi") ! `{.}: {bin:length(unparsed-binary(.))} bytes`'
"orders.schema.exi: 1573 bytes"
"orders.schema.deflate.exi: 837 bytes"

A third less than without the schema, and the decoder needs the same schema to read it. It also changes what comes back. A value written as a decimal is read back as the decimal, in its canonical form, the white space between elements of element-only content is gone (the schema says it means nothing), and the attributes come in the order of their names:

$ sxml xpath --input-format=exi --schema=orders.xsd --context-item=orders.schema.exi '(//line)[1], (//total)[1]'
<line price="89.0" quantity="3" sku="KB-104">Mechanical keyboard</line>
<total currency="EUR">320.9</total>

When the text of a value matters, --preserve=lexical-values keeps it, at the cost of writing it as text:

$ sxml encode --schema=orders.xsd --preserve=lexical-values --output=orders.lexical.exi orders.xml
$ sxml xpath --input-format=exi --schema=orders.xsd --preserve=lexical-values --context-item=orders.lexical.exi \
    '(//line)[1], (//total)[1]'
<line price="89.00" quantity="3" sku="KB-104">Mechanical keyboard</line>
<total currency="EUR">320.90</total>

A schema-informed stream is not a validation: a document the schema does not allow is still written, with the productions EXI keeps for what the schema did not foresee, at some cost in size. A status the enumeration lacks comes back as it was:

$ printf '<orders date="2026-11-27"><order id="A-1" status="lost"/></orders>' > lost.xml
$ sxml encode --schema=orders.xsd --output=lost.exi lost.xml
$ sxml xpath --input-format=exi --schema=orders.xsd --context-item=lost.exi 'string(//order/@status)'
"lost"

With --strict, those productions are left out: such a document cannot be written, and the streams are smaller still:

$ sxml encode --schema=orders.xsd --strict --output=lost.strict.exi lost.xml
sxml encode: lost.xml: content the schema-informed grammar has no production for
$ sxml encode --schema=orders.xsd --strict --output=orders.strict.exi orders.xml
$ sxml xpath 'bin:length(unparsed-binary("orders.strict.exi"))'
1426

To check a document against its schema, and to learn what is wrong with it, validate it (see Validating with XSD).

One stream for one document

Two documents that mean the same can make different streams. order-a.xml and order-b.xml are the same order, with the attributes in another order and the tags laid out differently; XPath finds them deep-equal, but the encoder writes the attributes as they come:

$ sxml encode --output=order-a.exi order-a.xml
$ sxml encode --output=order-b.exi order-b.xml
$ sxml xpath 'deep-equal(doc("order-a.xml"), doc("order-b.xml")), unparsed-binary("order-a.exi") = unparsed-binary("order-b.exi")'
true()
false()

Canonical EXI, a W3C Recommendation of its own, fixes every choice the format leaves to the encoder: the attributes and namespace declarations are sorted, each event takes the most specific production of the grammar that fits it, and the header carries the options. With --canonical, the same document always gives the same bytes, so a stream can be hashed, signed or compared byte for byte:

$ sxml encode --canonical --output=order-a.canonical.exi order-a.xml
$ sxml encode --canonical --output=order-b.canonical.exi order-b.xml
$ sxml xpath 'unparsed-binary("order-a.canonical.exi") = unparsed-binary("order-b.canonical.exi")'
true()
$ sxml decode order-b.canonical.exi
<order id="A-1007" status="paid"><line quantity="2" sku="HD-310"/></order>

The decoder needs no flags for it: the options are in the header. --omit-options-document leaves them out, when both sides know them, and --utc-time writes the date-times a schema types in UTC, so that one instant written in two time zones gives one stream.

Querying EXI

A command that reads a document reads EXI with --input-format=exi, taking the same option flags:

$ sxml xpath --input-format=exi --context-item=orders.exi 'count(//order), sum(//total)'
40
1.45528e4
$ sxml xpath --input-format=exi --context-item=orders.deflate.exi --alignment=compression \
    '//order[@status = "refunded"]/@id/string()'
"A-1006"
"A-1007"
"A-1008"
"A-1011"
"A-1021"
"A-1027"
"A-1028"
"A-1037"
"A-1038"

Inside a query, exi:serialize makes the stream of a node, as xs:base64Binary, and exi:parse reads one back. Their options are a map, whose options entry is the stream's options written as the EXI options document of the standard, the header element in the namespace http://www.w3.org/2009/exi:

$ sxml xquery --allow-file-access --method=text --expression='
    let $options := <header xmlns="http://www.w3.org/2009/exi">
                      <common><compression/></common>
                    </header>
    let $stream := exi:serialize(doc("orders.xml"), { "options": $options })
    return (bin:length($stream),
            deep-equal(exi:parse($stream, { "options": $options }), doc("orders.xml")))'
1011 true

The prefix exi is bound to sxml's namespace for EXI, urn:sxml:exi, in the sxml command and the JavaScript package; a stylesheet declares it. A query or a stylesheet can also write its result as EXI with the output method exi:exi:

$ sxml xquery --context-item=orders.xml --output=paid.exi \
    --expression='declare option output:method "exi:exi"; <paid>{//order[@status = "paid"]}</paid>'
$ sxml xpath --input-format=exi --context-item=paid.exi 'count(/paid/order)'
24
